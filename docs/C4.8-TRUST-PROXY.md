# C4.8 — Audit jurnalidagi IP haqiqiy mijoz IP'si bo'lsin

**Holat (2026-10-03):** bosqichlar soni (`TRUST_PROXY_HOPS`) o'rniga ichki
tarmoq bo'yicha ishonchga o'tildi — pastdagi "Yangilanish" bo'limi. Undan
keyingi bo'limlar tarix uchun qoldirildi: muammo va o'lchov o'zgarmagan,
yechim o'zgargan.

## Yangilanish (2026-10-03): nega bosqichlar soni yetmadi

Storefront (`<domen>`) brauzer so'rovlarini o'zining `/api/backend/*`
proksisi orqali ichki tarmoqdan to'g'ridan-to'g'ri api-gateway'ga yuboradi.
Ya'ni API'ga ikki xil uzunlikdagi zanjir keladi:

```
api.<domen>: mijoz → Cloudflare → cloudflared → caddy      → api-gateway
<domen>:     mijoz → Cloudflare → cloudflared → storefront → api-gateway
```

Proksi `X-Forwarded-For` ni uzatmaganda barcha xaridorlar storefront
konteynerining bitta IP'si bo'lib ko'rinardi — login limiti (5/daqiqa)
butun sayt uchun bitta bo'lib qolardi. Uzatganda esa `TRUST_PROXY_HOPS=2`
bilan teskarisi: storefront Next.js `cloudflared` manzilini ro'yxatga qo'sha
olmaydi (route handler soketni ko'rmaydi), shuning uchun ro'yxat bir bo'g'in
qisqa keladi va mijoz yozgan `X-Forwarded-For: 203.0.113.9` jurnalga
tushardi. `apps/api-gateway/src/trust-proxy.spec.ts` buni eski qiymat bilan
qizil, yangisi bilan yashil qilib ko'rsatadi.

**Yechim:** Express'ga son emas, ishonchli tarmoqlar beriladi
(`loopback, linklocal, uniquelocal` — `apps/api-gateway/src/trust-proxy.ts`).
Express ro'yxatni o'ngdan yuradi, ichki Docker manzillarini (172.16/12)
tashlab, birinchi ommaviy manzilni oladi — Cloudflare yoki Caddy qo'shgan
haqiqiy mijoz IP'si. Mijoz yozgan qiymatlar undan chapda turadi va ularga
navbat yetmaydi. Caddy ham aynan shunday ishlaydi
(`trusted_proxies static private_ranges`). Natija zanjir uzunligiga bog'liq
emas: tunnel yoqilsa/o'chirilsa yoki yangi ichki proksi qo'shilsa hech narsa
sozlanmaydi.

| Zanjir                                         | `req.ip`        |
| ---------------------------------------------- | --------------- |
| `cloudflared → caddy → api-gateway`            | mijoz           |
| `cloudflared → storefront → api-gateway`       | mijoz           |
| `caddy → api-gateway` (tunnelsiz)              | mijoz           |
| mijoz o'zi `X-Forwarded-For` yozsa (har qaysi) | baribir mijoz   |
| storefront `X-Forwarded-For` uzatmasa          | storefront IP'si |

**Storefront sharti:** proksi kelgan `X-Forwarded-For` ni **o'zgartirmasdan**
uzatadi — chapdagi qiymatni tanlab olmaydi (u mijoz yozgan bo'lishi mumkin)
va o'zi yangisini yasamaydi.

**Chegarasi:** ommaviy IP'li proksi zanjirga qo'shilsa (masalan tunnelsiz
Cloudflare proxy), uning tarmoqlari `trust-proxy.ts` ga ham, Caddy'ning
`trusted_proxies` ga ham qo'shilishi kerak — aks holda IP o'sha proksiniki
bo'lib ko'rinadi (soxtalashtirish emas, faqat noaniqlik).

**Serverda:** `TRUST_PROXY_HOPS` endi o'qilmaydi. `.env.production` da qolsa
zararsiz, `scripts/validate-production-env.sh` faqat olib tashlashni eslatadi.

## Muammo

`/admin/audit` dagi yozuvlarning hammasida IP bir xil edi — `172.20.0.6`.
Bu mijoz emas, **cloudflared konteynerining ichki manzili**.

Audit jurnalining butun ma'nosi "kim, qachon, QAYERDAN" degan savolga javob
berishda. Uchinchi savolga javob yo'q bo'lsa, nizo yoki suiiste'mol
tekshiruvida jurnal foydasiz. Ayniqsa `user.impersonate` (nomidan kirish)
yozuvlari uchun — prod bazada ularning 13 tasi bor va hammasi anonim.

## Ildiz sabab

`apps/api-gateway/src/main.ts:24`:

```ts
app.set('trust proxy', config.get<number>('TRUST_PROXY_HOPS', 1));
```

Sukut qiymati **1**, prodda esa bu kalit umuman berilmagan. Lekin zanjir
ikki bosqichli:

```
mijoz → Cloudflare edge → cloudflared → caddy → api-gateway
                          └──────── ishonchli 2 bosqich ────────┘
```

Express `trust proxy = N` da `X-Forwarded-For` ro'yxatining oxiridan N ta
manzilni "o'ziniki" deb tashlab yuboradi. N=1 bo'lganda mijoz IP'si emas,
cloudflared'niki qoladi.

## O'lchov (2026-09-21, jonli)

Caddy'ning kirish logi (`docker logs marketplace-caddy-1`, JSON format):

```
remote_ip        : 172.20.0.6          ← cloudflared konteyneri
client_ip        : 62.164.155.87       ← haqiqiy mijoz
X-Forwarded-For  : ["62.164.155.87"]
Cf-Connecting-Ip : ["62.164.155.87"]
```

Caddy proksilaganda XFF ga o'z ko'rgan manzilini qo'shadi, ya'ni
api-gateway'ga `62.164.155.87, 172.20.0.6` yetib boradi, soket manzili esa
caddy'niki. Express ro'yxati (soketdan orqaga):

| `TRUST_PROXY_HOPS` | `req.ip` natijasi        | baho              |
| ------------------ | ------------------------ | ----------------- |
| 1 (hozirgi sukut)  | `172.20.0.6`             | ❌ cloudflared     |
| **2**              | `62.164.155.87`          | ✅ haqiqiy mijoz   |
| 3 va undan ko'p    | mijoz yuborgan XFF qiymati | ⚠️ SOXTALASHTIRISH |

Prod bazasidagi tasdiq:

```sql
SELECT meta->>'ip' AS ip, count(*), max(created_at)::date
FROM identity.activity_log WHERE meta ? 'ip' GROUP BY 1 ORDER BY 2 DESC;

 172.20.0.6     | 45 | 2026-09-17   ← tunnel qo'shilgandan keyin
 62.164.155.182 |  5 | 2026-09-11   ← tunneldan oldin, to'g'ri ishlagan
 127.0.0.1      |  2 | 2026-09-18   ← serverning o'zidan qilingan so'rov
```

`cloudflared` konteyneri ~2026-09-12 da qo'shilgan — sana chegarasi aynan
mos keladi.

## Nega aynan 2, ko'p emas

`TRUST_PROXY_HOPS` ni keragidan katta qo'yish **xavfsizlik nuqsoni**:
mijoz o'z so'roviga `X-Forwarded-For: 1.2.3.4` sarlavhasini qo'shib
yuborsa, Express uni ishonchli deb qabul qiladi va audit jurnaliga soxta
IP tushadi. Ya'ni jurnalni buzish uchun bitta `curl` yetadi.

Qoida: **qiymat = o'zimiz nazorat qiladigan proksilar soni**, na ko'p, na kam.

## Zanjir o'zgarsa

| Zanjir                                   | Qiymat |
| ---------------------------------------- | ------ |
| `cloudflared → caddy → api-gateway`      | 2      |
| `caddy → api-gateway` (tunnel o'chirilsa) | 1      |
| To'g'ridan-to'g'ri (proksisiz, lokal dev) | 0      |

Tunnel `COMPOSE_PROFILES=tunnel` bilan yoqiladi
(`docker-compose.prod.yml` → `cloudflared.profiles`). Shuning uchun
`scripts/validate-production-env.sh` shu profilga qarab kutilgan qiymatni
o'zi hisoblaydi va mos kelmasa deploy'ni **to'xtatadi** — bu qiymat
jimgina 1 ga qaytib qolmasligi uchun.

## Qolgan qadam (serverda, qo'lda)

## Tekshirish (TC1 va TC2)

Kirish (`auth/login`) audit jurnaliga yozilmaydi — jurnalga tushadigan amal
kerak. Eng xavfsizi `reprovision`: u idempotent va 2026-09-18 da allaqachon
bir marta bajarilgan (yangi market ochmaydi).

**TC1 — haqiqiy IP ko'rinadi.** Tashqaridan (server ichidan EMAS, aks holda
`127.0.0.1` chiqadi) admin tokeni bilan:

```sh
curl -sX POST https://api.elchimarket.uz/api/v1/admin/integration/shops/4/reprovision \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

so'ng:

```sql
SELECT created_at, action, meta->>'ip' FROM identity.activity_log
ORDER BY created_at DESC LIMIT 1;
```

Kutilgan: `meta->>'ip'` = so'rov yuborilgan kompyuterning tashqi IP'si
(`172.20.0.x` EMAS).

**TC2 — soxta sarlavha jurnalga tushmaydi.** Xuddi shu so'rovga
`-H 'X-Forwarded-For: 203.0.113.9'` qo'shing. Jurnalda baribir haqiqiy IP
turishi kerak, `203.0.113.9` emas. Agar `203.0.113.9` chiqsa — qiymat
keragidan katta qo'yilgan.
