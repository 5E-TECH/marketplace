# C1.45 — Buyurtma shipment yorlig‘i

## Endpointlar

```http
GET  /api/v1/seller/orders/:id/label          # SELLER / OPERATOR, :id = seller-order
POST /api/v1/seller/orders/labels             # { "orderIds": ["101", "102"] }

GET  /api/v1/admin/orders/:id/label                          # :id = sales_order
GET  /api/v1/admin/orders/:id/sellers/:sellerOrderId/label   # bitta posilka
POST /api/v1/admin/orders/labels                             # orderIds = sales_order id
POST /api/v1/admin/orders/shipment-tokens/sync               # SUPERADMIN, backfill
```

Javob `application/pdf`, `Content-Disposition: attachment`. Har bir yorliq
100x60 mm (termal printer) alohida sahifa; partiya 1–100 ta.

### Admin id fazosi

Admin endpointlaridagi `:id` / `orderIds` — **sales_order** id, ya’ni admin
ro‘yxati, `GET /admin/orders/:id` va `:id/cancel` bilan bir xil. Bitta
buyurtmada bir nechta do‘kon bo‘lsa, har do‘kon posilkasi alohida sahifa
bo‘lib chiqadi. Ilgari yorliq endpointi bu id’ni seller-order id deb o‘qirdi:
ikki do‘konli buyurtmadan keyin ketma-ketliklar ajralib, admin boshqa
xaridorning yorlig‘ini chop etardi.

## Yorliqda

- Elchi shipment ID, marketplace va seller-order ID;
- Elchi `qr_code_token` qiymatidan yaratilgan QR;
- jo‘natuvchi do‘kon nomi;
- qabul qiluvchi ismi, telefon, viloyat/tuman va manzil;
- mahsulot nomlari va miqdori — 100x60 mm ga 4 ta satr sig‘adi, qolgani
  "+ yana N ta pozitsiya" (to‘liq tarkib Elchi’da va buyurtma tafsilotida);
- kuryer oladigan summa: Elchi `to_be_paid`, u bo‘lmasa bizdagi `cod_amount`.

## QR token

- Token posilka yaratilganda Elchi javobidan olinib
  `checkout.sales_order_seller.qr_code_token` ga, summa esa
  `elchi_to_be_paid` ga yoziladi — sotuvchi qo‘lda yaratganda ham, xaridor
  tasdiqlagan/to‘lagan paytdagi asosiy oqimda ham.
- Token bazada bo‘lmasa (eski satrlar) yorliq so‘ralganda Elchi
  `GET /partner/shipments/:id` dan olinib saqlanadi (Elchi uni `tracking`
  maydonida beradi).
- Buyurtma id’sini QR ga yozish (Elchi frontidagi fallback) ataylab yo‘q:
  Elchi skaneri (`order.find_by_qr`) faqat `qr_code_token` bo‘yicha qidiradi.
- Elchi skanerlab `received` webhook yuborganda seller-order `RECEIVED`
  holatiga o‘tadi va tarixga yoziladi.

## Xatolar

- SELLER faqat o‘z do‘koni, OPERATOR JWT dagi `shopId` doirasida.
- Begona yoki mavjud bo‘lmagan buyurtma `404`.
- Posilka yaratilmagan, yoki token na bazada, na Elchi’da bo‘lsa `409`.
- Partiyada chiqmagan yorliqlar PDF ni yiqitmaydi: `X-Labels-Skipped`
  headerida URI-encoded JSON `[{ orderId, sellerOrderId?, reason }]`.
  Birortasi ham chiqmasa `409`, sabablar bo‘yicha guruhlangan xabar bilan.

## Prod backfill (bir martalik)

Xaridor oqimi 2026-09 gacha tokenni saqlamagan (7, 8, 11, 14, 15-satrlar),
9-satrda esa qo‘lda yozilgan test tokeni turibdi. Deploydan keyin SUPERADMIN:

```bash
# 1) nima o‘zgarishini ko‘rish
curl -X POST "$API/api/v1/admin/orders/shipment-tokens/sync" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"dryRun": true}'
# 2) yozish; javobdagi nextAfterId null bo‘lguncha afterId bilan takrorlash
curl -X POST "$API/api/v1/admin/orders/shipment-tokens/sync" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"afterId": "0"}'
```

Eslatma: 9-buyurtma bizda `DELIVERED`, Elchi’da esa `new` — bu 09-17 dagi
sun’iy webhookdan qolgan; tokenni tuzatish holatni tiklamaydi, uni alohida
qo‘lda to‘g‘rilash kerak.
