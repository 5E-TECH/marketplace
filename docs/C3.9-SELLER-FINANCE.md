# C3.9 — Sotuvchi moliyasi (backend)

Wire format: `API_CONTRACT.md` §7.2. Bu hujjat — qarorlar va qo'lda tekshirish.

## Nima qilindi

Yangi hisob-kitob yo'q: admin `/admin/finance/*` dagi mavjud ledger, payout va
COD reconciliation ma'lumoti sotuvchiga faqat o'z do'koni kesimida ochildi.

| Endpoint | Manba |
|---|---|
| `GET /seller/finance/ledger` | `finance.ledger.list` (admin bilan bir xil) + `dateFrom/dateTo` |
| `GET /seller/finance/payouts` | `finance.payouts.list` (admin bilan bir xil) |
| `GET /seller/finance/summary` | `finance.seller.summary`: balans + payout jamlari + `/admin/finance/reports` + `nextPayoutDate` |
| `GET/PUT /seller/finance/payout-schedule` | yangi `finance.payout_schedule` jadvali |

`dateFrom/dateTo` admin ledger'iga ham qo'shildi. Admin va sotuvchi
endpointlarining javoblari Swagger'da DTO bilan hujjatlashtirildi
(`libs/common/src/dto/finance-response.dto.ts`).

## Qarorlar (Uzum/WB uslubida)

| Savol | Qaror |
|---|---|
| Kim ko'radi | Faqat **SELLER** (do'kon egasi). OPERATOR buyurtmalar bilan ishlaydi (PRD §12.1), pul ma'lumotiga kirmaydi → `403`. |
| Do'kon qayerdan | Token egasidan (`seller.shop.get-me`, ownerUserId). Query'da `shopId` yuborilsa global `forbidNonWhitelisted` → `400`. Do'kon topilmasa finance'ga so'rov ketmaydi (`404`). |
| Jadvalni kim tanlaydi | Sotuvchi o'zi, do'kon bo'yicha. Tanlamagan bo'lsa — **WEEKLY** (WB'dagi default haftalik). |
| To'lov kunlari | DAILY — har kuni; WEEKLY — dushanba; MONTHLY — oyning 1-kuni. Sana Asia/Tashkent bo'yicha. |
| `nextPayoutDate` | Bugungi tushum o'tadigan eng yaqin to'lov kuni — **doim bugundan keyin** (bugungi to'lov allaqachon o'tgan bo'lishi mumkin). Dushanba kuni WEEKLY → keyingi dushanba. |
| Summary davri | `dateFrom/dateTo` faqat davr ko'rsatkichlariga: `paidPayoutAmount` (`paid_at`) va `cod` (`settled_at`). `balance`, `pendingPayoutAmount` (PENDING+APPROVED), `heldPayoutAmount` — hozirgi holat. |
| Davr chegarasi | Kun bo'yicha, `dateTo` kuni ham kiradi — `/admin/finance/reports` bilan bir xil helper (`finance-query.util.ts`). |

## Cheklov — jadval hozircha ma'lumot uchun

Payout'larni hali ham SUPERADMIN qo'lda tasdiqlaydi va o'tkazadi
(`/admin/finance/payouts/:id/approve|release`). Jadval bu jarayonni
avtomatlashtirmaydi va admin ro'yxatida do'kon chastotasi ko'rinmaydi.

Kelgusi ishlar (bu cardga kirmaydi):
- admin payout ro'yxatida do'kon jadvali / "to'lov kuni keldi" filtri;
- jadval bo'yicha payout'larni avtomat yig'ish (cron). Fon vazifalari
  endi barcha servislarda ishlaydi (`app.init()` tuzatishi — `C4.6-RUNBOOK.md`).

## Qo'lda tekshirish

```bash
# Sotuvchi tokeni bilan
curl -H "Authorization: Bearer $SELLER_TOKEN" \
  "http://localhost:3000/api/v1/seller/finance/summary?dateFrom=2026-09-01&dateTo=2026-09-30"
curl -H "Authorization: Bearer $SELLER_TOKEN" \
  "http://localhost:3000/api/v1/seller/finance/ledger?dateFrom=2026-09-01&limit=50"
curl -H "Authorization: Bearer $SELLER_TOKEN" \
  "http://localhost:3000/api/v1/seller/finance/payouts?status=PENDING"

curl -H "Authorization: Bearer $SELLER_TOKEN" \
  http://localhost:3000/api/v1/seller/finance/payout-schedule      # WEEKLY, isDefault:true
curl -X PUT -H "Authorization: Bearer $SELLER_TOKEN" \
  -H "Content-Type: application/json" -d '{"frequency":"DAILY"}' \
  http://localhost:3000/api/v1/seller/finance/payout-schedule      # DAILY, ertangi sana
```

Kutilgan natijalar:
- TC1: ledger/payouts faqat shu do'kon yozuvlari; admin `?shopId=<o'sha do'kon>` bilan bir xil.
- TC2: `?shopId=1` qo'shilsa → `400`; OPERATOR yoki BUYER tokeni → `403`.
- TC3: summary `balance` = ledger'dagi eng oxirgi `balanceAfter`; `cod` = `/admin/finance/reports?shopId=...` bilan bir xil davr uchun.
- TC4: `{"frequency":"YEARLY"}` → `400`; DAILY/WEEKLY/MONTHLY saqlanadi, qayta GET'da `isDefault:false`.
- TC5: `nextPayoutDate` — DAILY ertaga, WEEKLY keyingi dushanba, MONTHLY keyingi oyning 1-kuni.
