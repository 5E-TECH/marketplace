# C4.6 production runbook

## Majburiy production sozlamalari

`.env.production.example` dan `.env.production` yarating. `DOMAIN` DNS A/AAAA
yozuvi serverga qarashi, serverda 80 va 443 portlar ochiq bo'lishi kerak. Caddy
sertifikatni avtomatik oladi va yangilaydi. GitHub production environment'ida
`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` va
secretlari bo'lishi kerak. `DEPLOY_DOMAIN` ixtiyoriy — berilmasa deploy
domenni serverdagi `.env.production` dagi `DOMAIN` dan o'qiydi.

`DOMAIN` (API) majburiy. `APP_DOMAIN` (sotuvchi kabineti) esa ixtiyoriy:
berilmasa Caddy `kabinet.localhost` zaxirasini ishlatadi — bu ichki sertifikat
bilan ishlaydi, public ACME'ga murojaat qilmaydi va API'ga ta'sir qilmaydi,
lekin kabinet tashqaridan ochilmaydi. Kabinetni chiqarishda `APP_DOMAIN` ni
qo'shing va `CORS_ORIGINS` ga ham o'sha domenni yozing — aks holda brauzerdan
hech bir so'rov o'tmaydi.

## Sotuvchi kabineti (frontend)

Frontend alohida repoda va alohida deploy bo'ladi
([`Marketplace-FrontEnd`](https://github.com/5E-TECH/Marketplace-FrontEnd) →
`DEPLOY.md`). Ulanish nuqtasi — shu stack yaratadigan `marketplace_edge`
tarmog'i: Caddy `{$APP_DOMAIN}` ni `frontend:8080` ga proxy qiladi.

**Tartib muhim:** avval backend stack'i ko'tariladi (tarmoq shunda yaratiladi),
keyin frontend. Frontend ko'tarilmagan bo'lsa Caddy `{$APP_DOMAIN}` da 502
qaytaradi — API bundan zarar ko'rmaydi.

```sh
docker network inspect marketplace_edge   # tarmoq bormi
docker ps --filter network=marketplace_edge
```

## Migratsiyani nazoratli ishga tushirish

Odatda migratsiya servis ko'tarilishida avtomat ishlaydi. Katta jadvalda uzoq
lock berish xavfi bo'lsa `.env.production` da `DB_AUTO_MIGRATE=false` qo'ying —
u holda migratsiyani deploy oldidan qo'lda bajarish kerak (aks holda servis
eski sxema bilan ishga tushadi va xato beradi).

## E2E smoke — ulanish tekshiruvi

Production test akkauntlari uchun quyidagi qiymatlarni berib ishga tushiring:

```sh
E2E_BASE_URL=https://api.example.com/api/v1 \
E2E_ADMIN_PHONE=+998900000001 E2E_ADMIN_PASSWORD=secret \
E2E_SELLER_PHONE=+998900000002 E2E_SELLER_PASSWORD=secret \
E2E_BUYER_PHONE=+998900000003 E2E_BUYER_PASSWORD=secret \
npm run test:e2e:smoke
```

Runner `deploy/e2e-smoke.json` dagi qadamlarni ketma-ket bajaradi. Yangi biznes
oqimlari shu JSON'ga request, response assertion va `capture` bilan qo'shiladi.
Secretlar JSON faylga yozilmaydi. Bu ssenariy **TC1 ni yopmaydi**: faqat
login, katalog va ro‘yxat endpointlarini tekshiradi. Login javobi raw
`accessToken`, register javobi esa `data.accessToken` formatida.

## TC1 — register → payment → shipment → payout

`deploy/e2e-payout.json` alohida ssenariy: yangi BUYER yaratadi, ajratilgan
mahsulotni savatga qo‘shadi, online checkout va payment yaratadi. To‘lovni
provayder orqali operator yakunlaydi; skript shu order `CONFIRMED` bo‘lishi
va haqiqiy shipment ID paydo bo‘lishini kutadi. Elchi’da yetkazilish tugagach,
aynan shu seller order `referenceId` ga tegishli payoutni topadi. SUPERADMIN
approve/release qilgandan keyin `PAID` va `paidAt` ni tekshiradi.

Oldindan faol test shop, Elchi ulanishi, qoldiqli test product/variant va
`admin/payments/providers/:provider` orqali sozlangan to‘lov provayderi kerak.
Provayder va Elchi test muhiti mavjud bo‘lsa undan foydalaning. Ssenariy
production callbacklarini soxtalashtirmaydi; haqiqiy provayder/Elchi amali
bo‘lmasa test kutish muddati tugab, xato bilan yakunlanadi.

Maxfiy `.env.e2e` faylda quyidagilarni sozlang (repo `.env.*` ni ignore qiladi):

```dotenv
E2E_BASE_URL=https://YOUR_API_DOMAIN/api/v1
E2E_ADMIN_PHONE=YOUR_ADMIN_PHONE
E2E_ADMIN_PASSWORD=YOUR_ADMIN_PASSWORD
E2E_NEW_BUYER_PHONE=UNUSED_TEST_PHONE
E2E_NEW_BUYER_PASSWORD=TEST_PASSWORD_MIN_8_CHARS
E2E_PRODUCT_ID=TEST_PRODUCT_ID
E2E_VARIANT_ID=TEST_VARIANT_ID
E2E_PAYMENT_PROVIDER=PAYME
E2E_ADDRESS=TEST_DELIVERY_ADDRESS
E2E_REGION_ID=TEST_REGION_ID
E2E_DISTRICT_ID=TEST_DISTRICT_ID
E2E_REPORT_FILE=/tmp/c46-e2e-report.json
E2E_SCENARIO_FILE=deploy/e2e-payout.json
```

```sh
node --env-file=.env.e2e scripts/e2e-smoke.mjs
```

Har run yangi, foydalanishga ruxsat berilgan test telefonini talab qiladi;
oldingi akkaunt/order/payout avtomatik o‘chirilmaydi. Reportdagi IDlar orqali
sinov yozuvlarini topish mumkin. Report token yoki parol saqlamaydi. Test shop
uchun oxirgi 100 payout ichidan `referenceId` bo‘yicha qidiriladi; ajratilgan,
kam trafikli test shop ishlating. Uzoq kutishda admin tokeni eskirsa runner
qayta login qiladi. POST amallari avtomatik qaytarilmaydi. To‘lovni kutish
30 daqiqa, yetkazilish 60 daqiqa, release 30 daqiqa; muvaffaqiyatsiz
qadam reportda `failed` bo‘ladi. Yakuniy `passed` bo‘lmagan run TC1 dalili emas.

## Sog'liq tekshiruvi

| Endpoint                | Nima tekshiradi                        | Kim ishlatadi           |
| ----------------------- | -------------------------------------- | ----------------------- |
| `/api/v1/health`        | Jarayon tirikmi (bog'liqliksiz)        | Docker healthcheck, Caddy |
| `/api/v1/health/readiness` | 11 servis + har birining DB ulanishi | Monitoring, deploy tekshiruvi |

`health/readiness` har mikroservisni RMQ orqali so'roqlaydi; servis o'z
Postgres ulanishini ham tekshiradi. Birortasi javob bermasa `503` va qaysi
biri yiqilgani qaytadi.
`health` esa hamisha `200` — vaqtincha yiqilgan bog'liqlik uchun konteynerni
qayta ishga tushirish muammoni hal qilmaydi.

## So'rovni kuzatish

Har javobda `X-Request-Id` sarlavhasi bor (tashqaridan kelgani hurmat
qilinadi). Xato javobida ham `requestId` qaytadi — foydalanuvchi shu ID'ni
aytsa, gateway log'idan aniq so'rovni topish mumkin:

```sh
docker compose -f docker-compose.prod.yml logs api-gateway | grep '<request-id>'
```

> Hozircha ID gateway darajasida ishlaydi. Uni RMQ orqali mikroservislarga
> uzatish alohida ish: `sendRpc` payload'ini o'zgartirish kerak bo'ladi.

## Monitoring va log

`monitor` API gateway va barcha muhim RabbitMQ queue consumerlarini har 30
sekundda tekshiradi. Ketma-ket uchta xatoda `ALERT_WEBHOOK_URL` ga `firing`,
tiklanganda `resolved` JSON yuboradi. Webhook javobi muvaffaqiyatsiz bo‘lsa
keyingi tickda qayta urinadi; `alert_delivered` logi faqat muvaffaqiyatli HTTP
javobdan keyin yoziladi. Recovery xatosi servis nosozligi sifatida sanalmaydi.
Tekshiruvlar ustma-ust ishlamaydi. Alert URL bo‘sh bo‘lsa `alert_unconfigured`
chiqadi va faqat lokal log yoziladi — bu TC3 uchun yetarli emas.

Payload `{service,status,detail,timestamp}`; Slack/Discord bevosita webhooki
uchun moslashtiruvchi adapter kerak.

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml logs -f monitor caddy
```

Alertni tekshirish uchun bitta servisni vaqtincha stop qilib, uch intervaldan
keyin webhook va monitor logini tekshiring; so'ng servisni qayta ko'taring.
Sinov oynasida `catalog-service` to‘xtashi katalog so‘rovlariga ta’sir qiladi.
`ALERT_WEBHOOK_URL` sozlanmagan bo‘lsa bu sinovni boshlamang.

```sh
# Production serverda, yangilangan monitor deploy qilingandan keyin:
cd /srv/marketplace
compose() { docker compose --env-file .env.production -f docker-compose.prod.yml "$@"; }
restore_service() { compose start catalog-service; }
trap restore_service EXIT INT TERM
compose stop catalog-service
# Alohida terminalda logs -f monitor: unhealthy → firing → alert_delivered.
# Alert qabul qiluvchi kanalda ham firing kelganini tasdiqlang.
# Standart threshold=3; har check + interval uchun kamida 2 daqiqa ajrating.
printf "Kanaldagi firing tekshirilgach Enter bosing: "
read -r confirmed
compose start catalog-service
# readiness=200, resolved → alert_delivered va kanaldagi resolved ni tekshiring.
trap - EXIT INT TERM
```

Har ikki alertning qabul qilingan vaqti, servis logi va tiklangandan keyingi
readiness javobini dalil sifatida saqlang. Faqat `firing` logi yetarli emas:
u webhook yuborilishidan oldin ham yoziladi.

## Backup va restore

Deploy workflow har deployda, `production-backup.yml` esa har kuni soat 02:15
(Toshkent vaqti) PostgreSQL custom-format backup oladi, SHA-256 yozadi va
alohida vaqtinchalik PostgreSQL 16 konteynerida restore qiladi.
Backup'lar serverdagi `/srv/marketplace/backups` ichida 14 kun saqlanadi.

Qo'lda tekshirish:

```sh
cd /srv/marketplace
sh scripts/db-backup.sh
sh scripts/db-restore-test.sh
```

Restore tekshiruvi live DBga yozmaydi: checksum, `pg_restore --exit-on-error`
va identity/catalog/checkout/payment/finance jadvallarini vaqtinchalik
konteynerda tekshiradi. Tayyorlik 60 urinish bilan chegaralangan; xatoda ham
konteyner o‘chiriladi. Backup xato bilan tugasa `.partial` fayl olib tashlanadi,
backup muvaffaqiyatli tugagandan keyingina `.dump` nomiga o‘tadi.
