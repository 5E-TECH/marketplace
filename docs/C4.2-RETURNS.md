# C4.2 — Qaytarish so'rovlari (returns) backend

Wire format: `API_CONTRACT.md` §7.1. Bu hujjat — biznes qoidalari, pul oqimi va
qo'lda tekshirish.

## Holatlar

```
SUBMITTED ──review──▶ IN_REVIEW ──approve──▶ APPROVED ──refund──▶ REFUNDED
    │                     │
    └──────reject─────────┴──────▶ REJECTED
```

- Xaridor yuboradi → `SUBMITTED`. Sotuvchi/operator tovarni qabul qilib
  tekshirishga olsa → `IN_REVIEW` (ixtiyoriy qadam).
- Sotuvchi `APPROVED` yoki `REJECTED` (sabab bilan) qiladi — **bir marta**.
- Admin nizoni yechadi: rad etilganni tasdiqlashi yoki tasdiqlanganni rad
  etishi mumkin (pul qaytarilgunicha).
- Pulni faqat **SUPERADMIN** qaytaradi (`APPROVED → REFUNDED`) — C6.4 dagi
  "pul chiqishi faqat SUPERADMIN" qoidasi bilan bir xil. Tasdiqning o'zi pul
  qaytarmaydi: pul chiqishi doim admin nazoratida.
- Har o'tish `return_request_history` ga yoziladi (kim, qaysi rol, izoh).

## Biznes qarorlari (Uzum Market uslubida)

| Savol | Qaror |
|---|---|
| Qaytarish muddati | Posilka `DELIVERED` bo'lgandan keyin **10 kun** (O'zbekiston qonuni bo'yicha sifatli tovar uchun muddat; Uzum ham shu). `RETURN_WINDOW_DAYS` env bilan o'zgaradi. Sana — `sales_order_seller_history` dagi birinchi `DELIVERED` yozuvi. |
| Nima qaytariladi | Faqat `DELIVERED` posilkadagi tovar, miqdor bo'yicha (qisman). Rad etilmagan so'rovlardagi miqdor band hisoblanadi — bir tovar ikki marta qaytmaydi. |
| Sabablar | `DEFECTIVE`, `DAMAGED`, `INCOMPLETE`, `WRONG_ITEM` — sotuvchi aybi (sifat). `NOT_AS_DESCRIBED`, `CHANGED_MIND`, `OTHER` (izoh majburiy). |
| Tovar sotuvchiga qanday qaytadi | Tizimdan tashqarida: Elchi integratsiyasida teskari posilka API'si yo'q. Xaridor tovarni sotuvchiga/topshirish punktiga olib boradi, sotuvchi qabul qilib tekshirgach tasdiqlaydi. |
| Omborga qaytadimi | Sifatli tovar (xaridor qarori) — **ha**, refund paytida qoldiq tiklanadi. Sifat muammosi bo'lgan tovar — **yo'q** (Uzum'dagidek brak sotuvchiga qaytariladi, qayta sotilmaydi). Admin `restock` bilan o'zgartira oladi. |
| Online to'lovda pul | Provayder to'lovidan faqat qaytarilgan summa (`payment_refund` jadvali). To'lov `PAID` qoladi; jami qaytarilgan summa to'lovga tenglashsa `REFUNDED`. |
| COD da pul | Naqd pulni Elchi to'g'ridan sotuvchiga beradi — platformada yo'q. Admin xaridorga pulni **qo'lda** (karta o'tkazma) qaytaradi va izohda qanday qaytarganini yozadi (majburiy). Summa sotuvchi hisobidan yechiladi (C6.4 TC5 "sotuvchi hisobidan yechiladi"). |
| Sotuvchi hisobi | Ledgerga `REFUND` = qaytarilgan summa − shu summaga to'g'ri keladigan komissiya (komissiya faqat sotilgan tovardan olinadi). To'lanmagan payout shuncha kamayadi; to'langan bo'lsa manfiy qoldiq keyingi online payout'dan ushlanadi (C4.3 netting). |
| Qisman summa | Admin so'rovdagi tovarlar summasidan kichik summa berishi mumkin (masalan xaridor aybi bilan shikast). Yetkazish narxi qaytarilmaydi. |

Muhim: provayder bilan real pul harakati. Payme/Click `payment.refund` hozir
ham (C3.6/C6.4 dagidek) faqat bazadagi holatni yozadi — pulni provayder
kabinetidan qaytarish amaliyoti o'zgarmadi. Qisman refundda ham summa
kabinetda qo'lda qaytariladi, tizim uni hisobga oladi.

## Bog'liq himoyalar

- `POST /admin/orders/:id/refund` (to'liq refund) buyurtmada `APPROVED` yoki
  `REFUNDED` qaytarish so'rovi bo'lsa `400` beradi — aks holda qisman
  qaytarilgan pul va qoldiq ikkinchi marta qaytib ketardi.
- To'liq qaytarilgan (`REFUNDED`) yoki bekor qilingan buyurtmaga qaytarish
  so'rovi yaratilmaydi.
- Refund oqimining har tashqi chaqiruvi (`payment.refund`,
  `inventory.return-order-items`, `finance.refund`) `return-refund:<id>`
  kaliti bilan idempotent — oqim o'rtada uzilsa, qayta chaqirish xavfsiz.

## Bildirishnomalar

`return.status-changed`: yangi so'rov → sotuvchiga; ko'rib chiqish/qaror →
xaridorga (admin sotuvchi qarorini o'zgartirsa sotuvchiga ham); pul
qaytarildi → ikkalasiga.

## Kelgusi ishlar (bu cardga kirmaydi)

- Elchi orqali teskari posilka (API paydo bo'lganda).
- Qaytarilmaydigan tovar toifalari (gigiyena va h.k.) — mahsulot kartasida belgi.
- Sotuvchi javob bermasa avtomatik eskalatsiya (Uzum: 20 kun).
- `GET /orders` da har tovar uchun "qaytarish mumkin …gacha" sanasi.

## Qo'lda tekshirish

Tayyorgarlik: online va COD buyurtma, posilkalari `DELIVERED`.

```bash
# 1. Xaridor so'rov yuboradi (TC1)
curl -X POST -H "Authorization: Bearer $BUYER_TOKEN" -H "Content-Type: application/json" \
  -d '{"items":[{"orderItemId":"31","quantity":1}],"reason":"DEFECTIVE","comment":"Ekranda chiziq"}' \
  http://localhost:3000/api/v1/orders/42/returns

# 2. Sotuvchi ko'radi, tekshirishga oladi va tasdiqlaydi
curl -H "Authorization: Bearer $SELLER_TOKEN" "http://localhost:3000/api/v1/seller/returns?status=SUBMITTED"
curl -X POST -H "Authorization: Bearer $SELLER_TOKEN" http://localhost:3000/api/v1/seller/returns/3/review
curl -X POST -H "Authorization: Bearer $SELLER_TOKEN" -H "Content-Type: application/json" \
  -d '{"comment":"Tekshirildi"}' http://localhost:3000/api/v1/seller/returns/3/approve

# 3. Admin ko'radi va qisman pul qaytaradi (TC2)
curl -H "Authorization: Bearer $ADMIN_TOKEN" http://localhost:3000/api/v1/admin/returns/3
curl -X POST -H "Authorization: Bearer $SUPERADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"amount":50000,"comment":"Qisman"}' http://localhost:3000/api/v1/admin/returns/3/refund
```

Kutilgan natija:

- 1-qadam: `201`, `status: SUBMITTED`; sotuvchiga bildirishnoma.
  Yetkazilmagan posilka, 11-kun yoki ortiq miqdor → `400`.
- 2-qadam: `history` da `SUBMITTED → IN_REVIEW → APPROVED`; xaridorga bildirishnoma.
  Boshqa do'kon sotuvchisi → `404`.
- 3-qadam: `REFUNDED`, `refundedAmount: 50000`, `restocked: false` (DEFECTIVE).
  `GET /admin/finance/ledger?shopId=…` da `REFUND` yozuvi (−50000 + komissiya
  ulushi). Takror chaqiruv yana `REFUNDED` qaytaradi, ledgerda ikkinchi yozuv
  paydo bo'lmaydi. `ADMIN_TOKEN` bilan refund → `403`.
- COD buyurtmada `comment` siz refund → `400`; izoh bilan → `REFUNDED`,
  provayderga so'rov ketmaydi, ledgerda `REFUND`.
